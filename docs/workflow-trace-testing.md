# HomeClaw Workflow Trace Testing Guide

This guide explains how to use the workflow trace testing framework end-to-end:

- run tests quickly in deterministic mode
- run integration tests against real Core
- inspect trace logs
- add new scenarios/contracts
- add targeted fixture data only when needed

---

## 1) What this framework tests

For each natural-language input, it validates the workflow sequence, including:

- model selection / routing
- tool calls
- skill calls
- plugin calls
- argument normalization
- fallback path and reason

It writes sequential JSONL traces to:

- `output/workflow_traces/*.jsonl`

---

## 2) Quick start (recommended)

From repo root:

```bash
python scripts/workflow_trace_runner.py --mode in_process_mock
```

This is the fastest mode for daily development and CI.

What you get:

- scenario pass/fail report in terminal
- trace files under `output/workflow_traces/`
- Markdown report is generated by default (disable with `--no-report-markdown`)

Run with YAML profile (recommended for automation):

```bash
python scripts/workflow_trace_runner.py --config tests/workflow_framework/run_profile.example.yml
```

## 3) Real Core integration mode

### 3.1 Use running Core

```bash
python scripts/workflow_trace_runner.py --mode real_core --base-url http://127.0.0.1:9000
```

Friendly report output (default):

```bash
python scripts/workflow_trace_runner.py --mode real_core --base-url http://127.0.0.1:9000
```

- default report path: `output/workflow_traces/reports/workflow-trace-<mode>-<timestamp>.md`
- optional custom path: `--report-markdown-path output/workflow_traces/reports/latest.md`
- disable markdown report for machine-only runs: `--no-report-markdown`
- full cleanup before run (remove all old traces/reports/slices): `--clean-all-traces`

### 3.2 Let runner start Core

```bash
python scripts/workflow_trace_runner.py --mode real_core --start-core
```

API key handling:

- `--api-key` optional
- auto-discovered from:
  1. `HOMECLAW_INBOUND_API_KEY` env
  2. `config/core.yml` -> `auth_api_key`
- when auth is disabled, runner retries without key

User ID handling (IM permission checks):

- `--user-id` optional
- auto-discovered from:
  1. `HOMECLAW_WORKFLOW_TEST_USER_ID` env
  2. first entry in `config/user.yml` under `users[*].im`
- if your Core enforces IM mapping, prefer an exact `im` identity (for example `matrix:@name:domain`)

Async /inbound polling (real LLM + tools can be slow):

- default wait per scenario: **600 seconds** (polls `GET /inbound/result` until `status` is `done` or `cancelled`)
- override: `--inbound-timeout 1200` or env `HOMECLAW_WORKFLOW_INBOUND_TIMEOUT_SEC=1200`

## 4) Run a single scenario

```bash
python scripts/workflow_trace_runner.py --mode in_process_mock --scenario daily_brief_ast_default
```

You can pass `--scenario` multiple times.

Clean run example:

```bash
python scripts/workflow_trace_runner.py --mode real_core --base-url http://127.0.0.1:9000 --clean-all-traces
```

Rerun only previously failed scenarios:

```bash
python scripts/workflow_trace_runner.py --mode real_core --base-url http://127.0.0.1:9000 --failed-only-from output/workflow_traces/reports/latest.json
```

## 5) YAML run profile (config-driven runs)

Use `--config <path.yml>` to control mode, scenario set, cleanup, real-core settings, and output files.

Reference example:

- `tests/workflow_framework/run_profile.example.yml`

Supported fields:

- `mode`: `in_process_mock` or `real_core`
- `clean_all_traces`: `true/false`
- `scenarios.include`: list of scenario IDs (empty = all)
- `scenarios.exclude`: optional exclusions
- `scenarios.failed_only_from`: JSON report path; run only failed scenario IDs from that report
- `real_core.base_url`, `real_core.start_core`, `real_core.api_key`, `real_core.user_id`, `real_core.inbound_timeout_sec`
- `outputs.markdown.enabled`, `outputs.markdown.path`
- `outputs.json.enabled`, `outputs.json.path`

Priority rule:

- CLI flags override YAML values.

## 7) Where scenarios and contracts live

- Scenarios: `tests/workflow_scenarios/*.yaml`
- Contracts: `tests/workflow_framework/contracts.yaml`
- Model profiles: `tests/workflow_framework/model_profiles.yaml`

Scenario example:

```yaml
id: daily_brief_ast_default
contract: daily_brief_ast_default
prompt: "今日新闻（20条，中文）"
description: "Daily brief should prefer vmprint path by default."
```

Contract example:

```yaml
contracts:
  daily_brief_ast_default:
    must_have_events:
      - event_type: skill_call_started
        details_contains:
          skill_name: daily-brief-1.0.0
      - event_type: arg_normalization
        summary: run_skill argv finalized
```

## 8) Add new scenario (step-by-step)

1. Add scenario YAML in `tests/workflow_scenarios/`.
2. Reuse existing `contract` or add a new one in `tests/workflow_framework/contracts.yaml`.
3. Run:

```bash
python scripts/workflow_trace_runner.py --mode in_process_mock --scenario <new_scenario_id>
```

4. Open produced trace JSONL and confirm event sequence is as expected.
5. Tighten contract assertions only for stable workflow invariants.

## 9) Add targeted fixture data only when needed

Most scenarios need no extra data.  
Only add fixtures when workflow depends on state (memory/history/files/external outputs).

Use this rule:

- If the same prompt can pass deterministically without extra state -> do not add fixture.
- If behavior depends on prior context -> add minimal fixture for that context only.

### 8.1 Fixture types

1. **Mock history/memory fixture** (preferred for in-process tests)
   - inject only required turns/records
   - keep small and explicit

2. **File fixture**
   - add tiny sample files under a test fixture folder
   - reference those files in scenario metadata

3. **External/API fixture**
   - mock adapter/plugin result
   - avoid live dependency in deterministic tests

### 8.2 Recommended pattern

Add metadata to scenario:

```yaml
id: summarize_with_history
contract: summarize_contract
prompt: "继续总结昨天的内容"
metadata:
  fixtures:
    memory: "fixtures/memory/summarize_seed.json"
```

Then in runner/harness:

- load fixture only if `metadata.fixtures` exists
- inject into mock context before executing prompt

### 8.3 Keep fixtures maintainable

- smallest possible data
- one fixture per behavior
- avoid giant snapshots
- document why fixture is required in scenario `description`

## 11) Troubleshooting

### No trace file generated

- ensure runner sets:
  - `HOMECLAW_WORKFLOW_TRACE=1`
  - `HOMECLAW_WORKFLOW_TRACE_DIR=...`
- verify write permission for `output/workflow_traces/`

### Scenario fails but response looks okay

- inspect contract: maybe too strict/non-stable assertion
- prefer checking invariant workflow events, not text phrasing

### All scenarios fail with `Events = 0`

This usually means **Core trace instrumentation is not enabled** for the process handling requests.

Typical symptom in Markdown report:

- every scenario has `Events` = `0`
- all failures are "missing required event ..."

Why:

- when using `--mode real_core --base-url ...`, runner talks to an already-running Core
- runner env vars do **not** automatically apply to that existing Core process

Fix options:

1. Let runner start Core (recommended):

```bash
python scripts/workflow_trace_runner.py --mode real_core --start-core --clean-all-traces
```

2. If you keep a manually started Core, restart it with trace env:

```bash
export HOMECLAW_WORKFLOW_TRACE=1
export HOMECLAW_WORKFLOW_TRACE_DIR=output/workflow_traces
python3 -m main start --no-open-browser
```

Then run runner with `--base-url ...`.

### Real-core auth errors

- pass `--api-key` explicitly, or set `HOMECLAW_INBOUND_API_KEY`
- confirm `config/core.yml` has correct `auth_api_key`

### IM permission denied (user_id not in im list)

- pass `--user-id` explicitly using one value from `config/user.yml` -> `users[*].im`
- or export `HOMECLAW_WORKFLOW_TEST_USER_ID` with that value
- for a quick check, run one scenario:
  - `python scripts/workflow_trace_runner.py --mode real_core --scenario daily_brief_ast_default --user-id "matrix:@your_id:matrix.org"`

### `TimeoutError: async inbound timed out`

- real Core often needs **more than 2 minutes** for one turn (LLM, tools, embedding warmup). Use `--inbound-timeout 1200` or set `HOMECLAW_WORKFLOW_INBOUND_TIMEOUT_SEC`.
- run **one** scenario first to confirm Core completes: `--scenario <id>`
- if it still never finishes, check Core logs: the request may be stuck (model down, blocking tool, etc.)

## 12) Suggested team workflow

1. During feature work:
   - run `in_process_mock` frequently.
2. Before merge:
   - run targeted scenarios for changed skills/tools/plugins.
3. For model change:
   - run same scenario set, collect traces, compare with baseline.
4. If regression:
   - use trace sequence + fallback events to locate logic branch quickly.
